# hono 実ネットワークでの遅延調査

測定日: 2026-10-24。対象: `hono@4.13.13`。既存の `live-hono.*` は変更していません。

## 結論

主な原因は、**全バージョンのメタデータ 6.31 MB を非圧縮で取得していること**です。
同じ CLI・JSON パーサー・公開バージョンを使う比較で、gzip を有効にするだけで平均 **343 → 179 ms（約48%短縮）** となりました。
HTTP/2 単独の改善は今回確認できず、最初に有効化するなら gzip が適切です。

## 4条件の A/B

各5サンプル。毎ラウンドで条件の順序をローテーション。
すべて `--no-cache`、HTTP 200、新規プロセス / Client / 接続。同じ 6,311,465 bytes の展開後 JSON を処理しています。

| 条件 | 実際の HTTP | プロセス全体 | ヘッダー受信まで | 本文取得・展開 | JSON解析 | バージョン解決 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 現状 | HTTP/1.1 | 342.9 ms | 77.2 ms | 223.5 ms | 28.6 ms | 0.46 ms |
| gzip のみ | HTTP/1.1 | 179.1 ms | 115.7 ms | 31.1 ms | 21.4 ms | 0.35 ms |
| HTTP/2 のみ | HTTP/2 | 358.8 ms | 80.0 ms | 234.9 ms | 30.4 ms | 0.46 ms |
| gzip + HTTP/2 | HTTP/2 | 197.1 ms | 130.3 ms | 32.9 ms | 22.7 ms | 0.35 ms |

ヘッダー待ちと本文取得が現状の約88%を占めます。
JSON 解析にも約29 ms、JSON ツリーの破棄にも約5 ms かかりますが、現在の最大の待ち時間は本文転送です。
解決・表示処理はそれぞれ約0.5 ms・0.1 ms で、ここを最適化しても今回の差の大部分は解消しません。

HTTP/2 は「必ず速い」とは限りません。今回のケースは1プロセスにつき1回の GET で接続を再利用せず、HTTP/2 の多重化の利点を測定しているわけではありません。
この小標本から HTTP/2 一般の性能や、gzip + HTTP/2 が常に不利とは判断しません。

詳細: [4条件比較](registry-transport-comparison.md) / [生サンプル](registry-transport-comparison.json)。

## 実際の圧縮サイズ

同じ reqwest を使う raw probe で自動展開を無効化し、`Content-Encoding: gzip` と gzip の先頭バイトを確認しました。

- 非圧縮本文: **6,311,465 bytes**
- gzip 本文: **267,786 bytes**
- 本文の転送量: **約95.8%減、約1/23.6**

これは HTTP 本文のサイズであり、HTTP ヘッダーや TLS フレームの byte 数は含みません。
raw probe は1回のサイズ確認で、上記の速度比較とは別です。

記録: [raw 本文サイズ](registry-payload-size.json)。

## キャッシュ利用時

同じ通常ビルドのウォーム済みキャッシュは平均 **13.4 ms**。
内部計測の `source: fresh-cache` により、ネットワーク Client を作成する前に返っていることを確認しました。

- ファイル読み込み・チェックサム・HTTP ポリシー読み込み: **9.4 ms**
- キャッシュ内のバージョン解決: **0.46 ms**

キャッシュ側で次に改善するなら、検索よりもファイル全体の読み込み・チェックサムのコストが候補です。
一方 `--no-cache` の比較では最低5分 TTL は意図どおり一切使われません。

詳細: [キャッシュ計測](registry-profile-cached.md) / [生サンプル](registry-profile-cached.json)。

## 現在の変更範囲

- 通常の feature は **rustls のみのまま**です。gzip / HTTP/2 を既定にはしていません。
- 比較用 `profile-gzip` / `profile-http2` feature と、`TNPM_PROFILE=1` の診断出力を追加しました。
- 診断は stderr のみで、通常の stdout・キャッシュ挙動は変更していません。
- 通常の release バイナリは `target/release/tnpm`、比較用バイナリは `target/profiles/` に分離しています。

再現手順: [ベンチ README](../README.md#通信解析時間の切り分け)。

## 制約と次の改善候補

- ライブネットワークなので CDN・回線・実行順・CPU の状態による変動があります。単独の最初の baseline 測定では本文取得の外れ値があったため、比較には4条件を交互に実行した結果を使いました。
- `headers_ms` は DNS/TCP/TLS/サーバー待ちの合計で、TLS 単体の時間は測っていません。
- gzip の自動展開後は reqwest が Content-Encoding / Content-Length を取り除くため、転送量の確認は別の raw probe で行いました。
- 優先順位は **gzip の本採用 → 必要なメタデータだけを構築する解析経路 → キャッシュ読み込みの高速化**。現在は単一フィールドの照会でも全バージョンの JSON を owned tree にしています。
- この調査は原因の切り分けです。既定 feature の変更や JSON 解析経路の最適化は、まだ行っていません。
