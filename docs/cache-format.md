# Registry cache binary format v3

保存先: `dirs::home_dir()/.tnpm/cache/v3/<hash先頭2桁>/<残り14桁>.bin`。
ハッシュは正規化済みのパッケージリクエスト URL の FNV-1a 64 bit。
レジストリのホスト・ポート・ベースパス・パッケージ名を含みます。
タグや範囲指定は URL に含めず、同じパッケージのデータを再利用します。

整数はすべて little endian。オフセットはファイル先頭からの絶対位置（u32）。
ファイル上限は 128 MiB、ノード復元は深さ 128・200 万ノードまで。

実験用の非互換形式です。v1 / v2 の読み込み・移行・フォールバックは実装しません。旧ファイルは削除せず、新しいレスポンスを v3 に保存します。旧形式しかない環境で `--offline` を使う前に、必要なパッケージのメタデータをオンラインで再取得してください。tarball / 展開済みパッケージのキャッシュ形式は変更しません。

## ヘッダー（88 bytes）

| Offset | Type | 内容 |
| --- | --- | --- |
| 0 | bytes[8] | `TNPMREG\0` |
| 8 | u32 | 形式バージョン `3` |
| 12 | u32 | ルートオブジェクトの位置 |
| 16 | u64 | レスポンス受信日時（Unix 秒） |
| 24 | u64 | HTTP ポリシーに基づく有効期限の概算（Unix 秒） |
| 32 | u32 | ファイル全体のサイズ |
| 36 | u32 | キー URL の UTF-8 バイト長 |
| 40 | bytes[16] | 自身を除くファイル全体の XXH3-128 チェックサム（little endian） |
| 56 | u32 | HTTP ポリシーノードの位置 |
| 60 | u32 | 本文文字列プールの位置 |
| 64 | u32 | 本文文字列プールのバイト数 |
| 68 | u32 | HTTP 文字列プールの位置 |
| 72 | u32 | HTTP 文字列プールのバイト数 |
| 76 | u32 | SemVer 順のバージョン索引の位置 |
| 80 | u32 | バージョン索引のエントリー数 |
| 84 | u32 | 全バージョン名が有効な SemVer なら `1`、それ以外は `0` |

88 byte 目から URL、その後に本文ノード群、バージョン索引、本文文字列プール、HTTP ポリシーノード群、HTTP 文字列プールを格納します。本文プールの直後が HTTP ノードの開始位置、HTTP プールの終端がファイル終端です。
ファイル名のハッシュだけで同一性を判断せず、URL 全体も検証します。
XXH3-128 は偶発的な破損の検出用です。FNV / XXH3 は暗号学的な認証や改ざんを防ぐセキュリティ境界には使いません。tarball の SRI は引き続き SHA-512 / SHA-256 / SHA-1 で検証します。

## ノード

| Tag | 型 | tag に続くデータ |
| --- | --- | --- |
| 0 | null | なし |
| 1 | false | なし |
| 2 | true | なし |
| 3 | number | u32 文字列位置、u32 長（数値の元の UTF-8 表現） |
| 4 | string | u32 文字列位置、u32 長 |
| 5 | array | u32 要素数、u32 子ノード位置 × 要素数 |
| 6 | object | u32 メンバー数、元の順の12 byteエントリー × 個数、キー順の u32 エントリー番号 × 個数 |

オブジェクトのエントリーは元のメンバー順で、次の u32 3 個です。

1. キー文字列の位置
2. キー文字列の UTF-8 バイト長
3. 値ノードの位置

キー検索は末尾の番号索引を二分探索して `O(log n)`。番号から元の順のエントリーと子ノードを直接参照します。復元は元のエントリー順に走査するだけで、v2 のような復元時のソートと補助配列は不要です。重複キーは元の順のまま保持し、検索では最初の値を使用します。

### 共有文字列プール

本文内のキー・文字列値・数値表現を同じプールでインターンし、同じテキストを1回だけ保存します。別バージョン間でもキー名、license、依存の範囲、説明などを共有できます。HTTP ポリシーは独立したプールを持ち、本文プールへの参照は作りません。

読み込み時に各プール全体を `simdutf8::basic` で一度だけ検証します。以後の参照は位置・長さ・UTF-8 文字境界を検証して借用し、同じテキストを繰り返し UTF-8 検証しません。`Value` が必要になった部分だけ所有文字列へ復元します。JSON のメンバー順・数値の元表現は維持します。

### SemVer 順の索引

各エントリーは `u32 バージョン名位置, u32 名前長, u32 マニフェストノード位置` の12 byteです。書き込み時にバージョン名を一度だけ解析し、SemVer 順に保存します。同じ SemVer 優先順位（build metadata 違いなど）は名前の辞書順で安定化します。読み込み時の全件ソートはありません。

通常の install は索引の末尾から探し、範囲に合う最新の1バージョンだけ復元します。peer の候補探索は必要な全バージョンを復元できます。全バージョン名が有効な SemVer ではない場合は早期終了せず、従来どおり不正な範囲・名前を検出します。タグ・完全一致はオブジェクト索引から直接検索します。

## 解決手順

1. ファイルサイズ・形式・URL・チェックサム・領域の境界・文字列プール・HTTP ポリシーを検証。期限切れでも再検証のために読み込み可能にする。
2. `Vary` に対応するリクエスト値を比較し、HTTP ポリシーから鮮度を判定。
3. `dist-tags`、明示バージョン、保存済みの SemVer 索引から必要なバージョンを決定。
4. 該当するマニフェストだけを復元。install は表示用のルートメタデータや全バージョン名配列を復元しない。
5. `view FIELD...` は対象フィールドが参照するルートキーだけ復元。フィールド指定なしの表示・JSON は全メタデータを維持し、公開する `versions` 配列も必要なときだけ作る。
6. 新鮮なら HTTP client / TLS / proxy の初期化もせずそのまま利用。古ければ client を作り ETag / Last-Modified を使って再検証し、304 なら本文を再利用、200 なら置換。

## HTTP ポリシーノード

同じ型付きバイナリノードで、次のオブジェクトを保存します。

- `response-headers`: `Cache-Control`, `Date`, `Expires`, `Age`, `ETag`, `Last-Modified`, `Vary`。値は文字列の配列で、同名ヘッダーの繰り返しも保持。
- `request-headers`: `Accept`, `Accept-Encoding`, `User-Agent` の送信値。`Vary` の照合に使用。
- `request-time-ms`, `response-time-ms`: リクエスト開始 / レスポンスヘッダー受信時刻（Unix ミリ秒）。

Authorization・Cookie などは保存しません。認証付きリクエストはキャッシュを利用しません。

鮮度は `max-age`、または `Expires - Date` から計算します。`Date` がなければ受信時刻を使います。
受信時点の age は `max(受信時刻 - Date, Age + 応答所要時間)` です。
通常は `max(サーバーの鮮度期間 - 受信時点の age, 300秒)` を、受信時点からの有効期間にします。TTL 未指定・単独の `max-age=0`・過去の Expires も最低300秒に引き上げます。
長い TTL は維持し、キャッシュ読み込み時には受信時刻や下限の起点を更新しません。
これは短いサーバー TTL を延長する tnpm 独自ポリシーです。`no-store` / `no-cache` / `must-revalidate` / 不正なヘッダーなどの明示的な制限がある場合は、最低300秒を適用しません。
ヘッダーの秒単位の期限は概算で、実際の判定には保存した HTTP ポリシーを用います。
`no-cache` や不正な鮮度指定は再検証を必要とし、`must-revalidate` がある場合はサーバーの TTL に従います。

304 ではキャッシュ関連ヘッダーをマージし、受信時刻と age の計算を更新します。
本文ノード・SemVer 索引・本文文字列プールはバイト列のまま維持し、末尾の HTTP ポリシー・HTTP プールと固定ヘッダー・チェックサムだけを再構築して、ファイル全体を原子的に置換します。
304 に異なる ETag が付いていた場合は本文を再利用せず、無条件 GET で再取得します。

ファイル自体の読み込みとチェックサム検証は `O(ファイルサイズ)` です。
高速化の主眼は JSON の再解析と、不要な全バージョンのオブジェクト割り当ての回避です。
ネットワーク JSON の解析と表示用 JSON の生成は引き続き `nojson` を使います。

ネットワーク本文は `simdutf8::compat::from_utf8` で検証し、詳細な UTF-8 エラーを保持しながら受信バッファを直接参照して解析します。本文全体を `Vec` / `String` へ複製しません。キャッシュのチェックサムが一致していても UTF-8 検証は省略しません。不正なプール、文字境界を破る参照、ノード範囲外のオフセット、深すぎる・循環するノードは `InvalidData` として拒否します。

書き込みは排他的に作成した同一ディレクトリの一時ファイルに完了させてから rename。
並行する writer は別の一時ファイルを使い、reader に途中の書き込みを見せません。
